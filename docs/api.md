# The API contract

What every endpoint answers: the success shape, the failure shape, and which
status code means what.

Only `GET /health/live` is built. Everything else is the contract it will be
built to, so a frontend or a reviewer can read the shape before the code exists.
What is and is not implemented is marked throughout.

---

## Every response carries a request ID

`X-Request-Id` is on every response, a UUID generated by the server. An inbound
`X-Request-Id` is ignored ([Q3](../DECISIONS.md)).

Every error body repeats it as `error.requestId`. That is the value to quote in a
report: it leads to the log line for that exact request.

---

## A failure is always `error`

One shape, every time, whatever went wrong:

```json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "The sending wallet does not have enough funds.",
    "requestId": "072ac170-44f7-4a0d-b8c6-68b6d2b24b77"
  }
}
```

`code` is for the caller's logic and is stable. `message` is for a human reading
a log or a screen. Neither ever carries an exception message, a stack, a file
path, a SQL fragment or a table name — an unexpected failure returns a fixed
message and nothing else ([Q4](../DECISIONS.md)).

---

## Status codes

| Code | Means |
| --- | --- |
| `200` | Done |
| `201` | Created |
| `400` | The request is malformed: a missing field, a negative amount, a non-integer `amountMinor` |
| `401` | No credentials, or they are invalid |
| `403` | Authenticated, but not allowed to do this |
| `404` | No such route, or no such record the caller may see |
| `409` | The same idempotency key with different transfer details |
| `422` | The request is valid and a business rule refuses it: insufficient funds, a restricted account |
| `429` | Rate limited. Carries `Retry-After` |
| `500` | An unexpected failure. No detail in the body |
| `503` | The database is unreachable, or a lock wait timed out. Retry a transfer with the same key |

**`400` versus `422`** is the distinction worth being precise about. `400` means
the request could never work — `amountMinor` is `"abc"`. `422` means the request
is well-formed and the answer is no — the amount is fine, the wallet cannot
afford it. A client retries a `422` after changing the world, not the request.

**`404` for another user's record, not `403`.** A transfer the caller is not a
party to is indistinguishable from one that does not exist. `403` would confirm
that the id is real, which is a way of enumerating other people's records.

**`503` is not a failure.** It means the outcome is unknown. A transfer that gets
a `503` may or may not have committed, and the only correct response is a retry
with the same idempotency key, which resolves it either way. See the known versus
unknown table in [domain.md](domain.md).

## Endpoints

| Endpoint | Access | Status |
| --- | --- | --- |
| `GET /health/live` | Public | **Built** |
| `GET /health/ready` | Public | Not built |
| `POST /auth/register` | Public | Not built |
| `POST /auth/login` | Public | Not built |
| `GET /wallets/me` | User | Not built |
| `POST /transfers` | User | Not built |
| `GET /transfers` | User | Not built |
| `GET /transfers/:id` | User | Not built |
| `POST /admin/users/:id/block` | Admin | Not built |
| `POST /admin/users/:id/unblock` | Admin | Not built |

### `GET /health/live` — built

Answers whether the process is up. It deliberately touches nothing else, so it
stays true while the database is unreachable.

```
200 { "status": "ok" }
```

### `GET /health/ready` — not built

Answers whether the database is reachable, and is the endpoint Render's health
check points at. `200` when a query succeeds, `503` when it does not.

Kept separate from liveness so a database outage is not reported as a dead
process, and so readiness is never answered before a real check exists.

### `POST /auth/register` — not built

Creates a user and their zero-balance NGN wallet in one transaction, so a user
can never exist without a wallet.

```json
{ "email": "ada@example.com", "password": "...", "name": "Ada" }
```

The email is trimmed and lowercased before uniqueness and blacklist matching —
the same normalisation used everywhere. The role is always `customer`; a body
containing `role`, `blocked`, `balance` or `is_system` is refused (**Q17**,
open). A blacklisted email cannot register.

`201` with the user and wallet. `400` malformed, `409` email taken, `422`
blacklisted.

### `POST /auth/login` — not built

`200` with a JWT. `401` on bad credentials, with the same message whether the
email is unknown or the password is wrong — distinguishing them tells an attacker
which emails are registered.

### `GET /wallets/me` — not built

The caller's own wallet. There is no endpoint for anyone else's. The wallet is
found from the token's user id, never from a parameter.

```json
{ "id": 7, "currency": "NGN", "balanceMinor": "150000" }
```

### `POST /transfers` — not built

The one that matters. Requires an `Idempotency-Key` header.

```json
{
  "sourceWalletId": 7,
  "destinationWalletId": 12,
  "currency": "NGN",
  "amountMinor": "150000"
}
```

**The sender always comes from the token.** `sourceWalletId` is checked for
ownership under lock and never grants it — a wallet id in a body is a claim, not
an authorisation.

`201` with the transfer and its reference. `400` malformed, `401` unauthenticated,
`403` not the caller's wallet, `409` key reused with different details, `422` a
business refusal, `429` rate limited, `503` uncertain — retry with the same key.

A replayed key returns the original response with the original status.

### `GET /transfers` — not built

Transfers the caller is a party to, newest first, paginated. Never anyone else's.

### `GET /transfers/:id` — not built

One transfer, if the caller sent or received it. `404` otherwise, including when
the transfer exists.

### `POST /admin/users/:id/block` and `/unblock` — not built

Admin only. The restriction change and its audit row commit together, so there is
no restriction without a record of who made it and why. Both lock the affected
user row, in the same order a transfer does, so blocking and transferring
serialise rather than interleave ([Q9](../DECISIONS.md)).

Unblocking does not lift a blacklist.

---

## What this does not cover yet

Pagination parameters and their defaults, the exact JWT lifetime, the full list
of `code` values, and the shape of the transfer reference. Each is settled with
the endpoint that needs it rather than guessed here.

`POST /admin/blacklist` and `DELETE /admin/blacklist/:id` are optional in the
build spec and currently out of scope (**Q20**, open).
